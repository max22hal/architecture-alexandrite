# Выбор и настройка мониторинга в системе

## Мотивация
Настройка мониторинга в системе необходима для ее стабильной работы. Мониторинг позаволит:
- Улучшить видимость и повысить безопасность системы. 
Видимость означает, что компания получит полное представление о работе системы. Высокие показатели видимости положительно влияют на общие показатели системы и подсвечивают ее слабые места. Команда получает полное представление о текущем состоянии системы: от нагрузки на сервисы до ошибок в отдельных модулях. Это помогает своевременно обнаруживать уязвимости и аномалии в поведении системы.
- Ускорить решение проблем и повысить надежность системы
При помощи мониторинга команда может быстрее определить причины возникновения проблемы. Следовательно, быстрее устранить ее и предотвратить в будущем. Своевременные алерты и логирование позволяют оперативно находить первопричины инцидентов, минимизируя время простоя и снижая влияние на клиентов. Это также снижает нагрузку на команду поддержки.
- Повысить быстродействия системы и помочь с распределением ресурсов
С помощью инструментов мониторинга можно выявлять узкие места. Например, сервисы, которые перегружены, или запросы, которые слишком долго обрабатываются. Это помогает оптимизировать производительность — появляется возможность проанализировать, как система работает под разными нагрузками.
- Ускорить рабочие процессы и DevOps
Мониторинг способствует оптимизации процессов и сокращению количества ошибок. Он ускоряет обратную связь при изменениях в коде и инфраструктуре. В свою очередь, это помогает ускорить рабочий процесс и улучшить взаимодействие между командами
- Получить важные бизнес-данные
Метрики мониторинга можно использовать не только для технического анализа, но и для оценки поведения пользователей, ключевых точек отказа и бизнес-метрик (например, количество успешных заказов в минуту). Это помогает принимать более обоснованные продуктовые и стратегические решения.
- Повысить удовлетворенность пользователей
Быстрое решение и/или предотвращение проблем, которые связаны с производительностью и функциональностью приложения значительно улучшает пользовательский опыт. Пользователь не видит сам мониторинг, но чувствует его эффект - система работает быстре и стабильнее

## Выбор подхода к мониторингу

В качестве подхода к мониторингу будет использоваться комбинация методов USE, RED и "Четыре золотых сигнала"

* USE - используется для MES и генерации 3D изображений. Также USE можно использовать для метрики очередей RabbitMQ
Эти компоненты сильно зависят от ресурсов. Расчёт стоимости, генерация 3D — CPU и память-интенсивные задачи, возможны очереди, перегрузки.

* 4 золотых сигнала - все API системы
Данный подход является наиболее общим и охватывает все, что необходимо для высоконагруженных API. Особенно хорошо этот метод подходит для CRM API и фронтового приложения. Также "4 золотых сигнала можно использовать как дополнительную метрику для MES API 

* RED - используется для мониторинга MES API
MES API участвует в расчётах, приёме заказов и их статусах — это критически важный интерфейс.
RED позволит понять:
- сколько запросов приходит
- сколько из них падают с ошибками
- сколько обрабатываются дольше нормы

## Список метрик

### RabbitMQ
Метрики используются для отоброжения состояния сообщений в RabbitMQ. RabbitMQ является критически важным элементом системы. 

1. Number of dead-letter-exchange letters in RabbitMQ
DLX метрика показывает когда сообщение не может быть обработано и перенаправленно в Dead Letter Exchange

2. Number of message in flight in RabbitMQ
Количество in-flight сообщений отражает общее состояние очереди

3. Message rates in RabbitMQ
- rabbitmq_messages_published_total
- rabbitmq_messages_delivered_total
- rabbitmq_messages_ack_total
Данная метрика показывает сколько сообщений публикуется, сколько сообщений доставленно и сколько сообщений подтверждено. Позволяет увидеть, сбалансированы ли производитель и потребитель. 
Если published > delivered — сообщения копятся.
Если delivered > ack — потребители не подтверждают сообщения, значит есть риск потери/повтора.

### MES API
Метрики для отслеживания состояния MES API

Метрики производительности MES API.

1. Number of requests (RPS) for MES API - количество запросов в секунду. Позволяет оценить нагруженность системы

2. Number of requests (RPS) per user for MES API - количество запросов в секунду от конкретного пользователя. Позволяет понять, есть ли у конкретного пользователя какие-то проблемы. Позволяет вовремя заметить DDoS атаку на систему

3. Number of HTTP 200 for MES API - количество успешных вызовов

4. Number of HTTP 500 for MES API - количество "упавших" вызовов. При росте данного показателя можно отследить возникновение проблем на стороне API

5. Rejected requests/timeouts for MES API - запросы, которые не были обслужены, даже если 500 коды не вернулись (например, отвалился клиент)

** Для первых пяти метрик можно добавить ярлыки method, env, endpoint для более точной работы ** 

6. Number of simultanious sessions for MES API - количество одновременных сессий для API. Метрика позволяет оценить нагрузку на систему

7. Response time (latency) for MES API - задержка, связанная с запросами. Позволяет отследить скорость работы системы

8. Kb tranferred (received) for MES API - размер полученных сообщений

9. Kb provided (sent) for MES API - размер отправленных сообщений

Cистемные метрики MES API

10. CPU % for MES API - потребление CPU. Позволяет оценить нагрузку на систему

11. Memory Utilisation for MES API - утилизация памяти для API. Позволяет оценить нагрузку на систему

12. Memory Utilisation for MES db instance - утилизация памяти для инстанса БД. Позволяет оценить нагрузку на БД

13. Size of MES db instance - размер инстанса базы данных. Позволяет оценить текущее состояние БД и прогнозировать необходимость масштабирования

1. Size of S3 storage - размер хранилища. Позволяет прогнозировать переполнение, планировать архивирование/очистку.

Ко всем метрикам можно добавить ярлыки env и bucket_name для определения окружения и бакетов.

## План действий

1. Развертывание и настройка time-series базы данных
* Выбрать и развернуть хранилище метрик (например: Prometheus).
* Настроить ротацию и хранение исторических данных (retention policy).

2. Интеграция агентов/экспортеров метрик
* Подключить экспортеры для:
    - RabbitMQ (например, rabbitmq_exporter)
    - S3 (через AWS SDK или метрики Yandex Object Storage)
    - API сервисов — встроенные/кастомные метрики (через Prometheus SDK или OpenTelemetry)
* Разработка и интеграция кастомных метрик в коде API

3. Настройка дашбордов в Grafana
* Создать дашборды для:
    - Общей картины по всем системам
    - RabbitMQ
    - MES API / CRM API / Shop API (по отдельности)
    - S3-хранилища
* Настроить фильтрацию по ярлыкам: env, endpoint, method, bucket_name, user_id и др.

4. Настройка алертов и уведомлений
* Настроить алерты по критическим метрикам: высокий latency, рост 500, перегрузка CPU, накопление сообщений в DLX и пр.
* Настроить интеграции с каналами оповещений: Slack / Пачка/ Email / Rocket

5. Организация мониторинга по подходам (USE, RED, 4 золотых сигнала)
* Для каждого сервиса применить выбранный подход:
    - USE для ресурсозависимых компонентов (3D генерация, RabbitMQ)
    - RED для MES API
    - 4 золотых сигнала для CRM и фронта

6. Документация и обучение команды
* Описать метрики, лейблы, алерты и их значение
* Создать гайд по добавлению новых метрик
* Провести короткий обучающий воркшоп для команды разработки

## Пороговые значения насыщенности и действия при их превышении

## RabbitMQ

| Метрика | Порог | Обоснование | Реакция |
|--------|-------|-------------|---------|
| `queue_messages_ready` | > 10 000 | Перегрузка очереди, потребители не справляются | Авто-тикет в Jira, алерт в Slack, масштабирование consumer'ов |
| `dead_letter_queue` | > 100 в 10 мин | Массовые ошибки в сообщениях | Тикет, логгирование DLX, уведомление DevOps |
| `message_ack_latency` | > 2 сек | Замедленная обработка сообщений, возможны дубли | Slack-алерт, рестарт сервисов, масштабирование |

## API (MES, CRM, Shop)

| Метрика | Порог | Обоснование | Реакция |
|--------|--------|-------------|---------|
| `http_500_rate` | > 5% в течение 1 мин | Ошибки на стороне сервиса | Slack-алерт, тикет, лог-анализ |
| `latency_p95` | > 1 сек | UX деградация, медленный отклик | Алерт, рестарт подов, тикет на оптимизацию |
| `rps_per_instance` | > 300 | Потенциальная перегрузка API | HPA/авто-масштабирование |


## Системные метрики

| Метрика | Порог | Обоснование | Реакция |
|--------|--------|-------------|---------|
| `CPU usage` | > 85% в течение 5 мин | Риск деградации и перегрева | Slack-уведомление, масштабирование |
| `Memory usage` | > 90% | Возможность OOM и краша | Тикет, рестарт подов, отладка утечек |
| `DB size` | > 90% диска | Возможен отказ БД | Алерт, уведомление DBA, масштабирование диска |


## S3 Хранилище

| Метрика | Порог | Обоснование | Реакция |
|--------|--------|-------------|---------|
| `storage_used` | > 80% от квоты | Риск переполнения и превышения бюджета | Уведомление фин. команды, политика архивирования |
| `bytes_uploaded_spike` | > 10x среднего | Аномальный трафик, рассинхронизация | Slack-уведомление, лог аудит |
| `number_of_objects` | > 10 млн | Торможение операций с бакетом | Скрипт агрегации, очистка |


## Действия при превышении порогов

- Автоматическое создание тикета 
- Уведомление в корпоративный мессенджер
- Горизонтальное масштабирование
- Автоматический рестарт подов
- Письмо в поддержку
- Звонилка/PagerDuty/on-call
