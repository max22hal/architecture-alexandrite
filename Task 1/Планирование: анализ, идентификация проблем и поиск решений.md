# Планирование: анализ, идентификация проблем и поиск решений

## Существующие и потенциальные проблемные места

1. CRM и MES не справляются с нагрузкой
2. На стороне API теряются заказы
3. MES работает медленно и перегружается. Даже после оптимизаций (фильтры, пагинация) производительность не улучшилась. Потенциально MES является "бутылочным горлышком"
4. Отсутствие кеширования часто запрашиваемых данных в MES. Например, дашбордов и заказов
5. Работа с 3D моделями не оптимизирована. "Тяжелые" модели обрабатываются в том же порядке, что и более легкие 
6. Заказ создается в CRM только после получения сообщения от MES. Если в одном из сервисов MES что-то пошло не так или сообщение потерялось в RabbitMQ, то заказ может "потеряться" 
7. Не настроен мониторинг "зависших" сообщений в MQ
8. Нет отслеживания ошибок интеграции
9. Нет логирования и трассировки запросов между сервисами
10. Нет контроля SLA и механизмов оповещения при просрочке заказов
11. Все приложения работают на одном EC2-инстансе каждый. В итоге нет отказоустойчивости, горизонтального масштабирования и балансировки нагрузки
12. Один инстанс БД используется для и чтения, и записи 
13. Потенциальная проблема - нет автоматического масштабирования. При резком росте нагрузки система "ляжет"
14. Нет автоматического тестирования. Судя по всему, приложения слабо покрыты тестами
15. Нет атоматических пайплайнов CI/CD

## Инициативы для устранения нежелательных ситуаций
1. Добавить ассинхронную обработку вызовов MES API (RabbitMQ). Реализовать retry, timeout и DQL логику. Это позволит снизить вероятность потери данных заказов про работе с API, а так же уберет необходимость ждать результатов расчетов онлайн
2. Добавить кеширование в MES для ускорения обработки заказов, отображения дашбордов, статических материалов и часто повторяющихся расчетов. Кеширование можно реалтзовать на уровне БД + Redis для горячих данных
3. Добавить очередь RabbitMQ между Shop API и хранилищем 3D моделей. Вынести обработку сложных 3D моделей в отдельную очередь. Добавить приоритезацию задач в очереди. Реализовать retry, timeout и DQL логику. Это позволит ускорить работу CRM и повысит удовлетворенность клиентов, так как более простые модели не будут ждать заверщения обработки более сложных. К тому же, это повысит отказоустойчивость системы
4. Добавить очередь RabbitMQ между CRM API и хранилищем 3D моделей. Реализовать retry, timeout и DQL логику.Это позволит снизить нагрузку на хранилище и повысить отказоустойчивость 
6. Настроить обработку ошибок и автоматические ретраи в RabbitMQ между MES API и СRM API. Это позволит повысить отказоустойчивость и снизить количество "потерянных" заказов
7. Реализовать отложенный расчет стоимости в MES. Если MES перегружен, то лучше принять заказ без расчета, чем не принять вообще
8. Добавить мониторинг зависших сообщений в RabbitMQ
9. Добавить отслеживание ошибок интеграции, логирование и трассировку запросов между сервисами. Это позволит повысить наблюдаемость приложения и увеличить скорость реакции поддержки на возникающие проблемы
10. Добавить алерты по SLA и просрочкам заказов. Это поможет повысить скорость реагирования и, как следствие, улучшит пользовательский опыт
11. Прогнозировать нагрузку и Capacity planning. Для этого необходимо собирать метрики по нагрузке, построить прогноз на 3-6 месяцев и заложить резерв мощностей заранее
12. Добавить реплицирование и шардирование инстансов БД. Разнести чтение и запись на разные шарды БД. Это позволит существенно повысить скорость взаимодействия с БД и повысить отказоустойчивость приложений
13. Настроить автоматическое масштабирование приложений. Это позволит лучше справляться с пиковыми нагрузками
14. Добавить автоматическое тестирование. Покрыть все критические сервисы приложений автотестами. Это позволит увеличить скорость работы команды разработки и снизить количество багов. Возможно, стоит нанять тестировщика с опытом создания автотестов
15. Настроить автоматические пайплайны CI/CD. Это позволит повысить скорость доставки продукта в продакшн и снизит количество ошибок при деплое
16. Вести контроль версий API и документацию. Это снизит число проблем у B2B клиентов.

## Инициативы в порядке приоритета

В качестве основных приоритев я бы выделил:
- Урон бизнесу от проблемы
- Сложность реалтзации
- Зависимость между инициативами
- Выгода "здесь и сейчас"

Приоритезированный список:
1. Ассинхронная обработка вызовов MES API
На текущий момент времени именно MES выглядит самым слабым звеном всей системы. Ассинхронная развязка между MES API и MES снизит риск потери заказов и снимит давление с MES

2. Ретраи и обработка ошибок между MES и CRM
Этот функционал критичен для целостности заказов и позволит сильно повысить отказоустойчивость

3. Реализация мониторинга, логирования, трассировки и мониторига зависших сообщений в RabbitMQ
Данный функционал позволит реализовать базовую наблюдаемость, необходимую для отладки всех следующих инициатив. Также он минимизирует репутационные потери и потери контрактов. Позволит выявлять проблемы еще до жалоб клиентов

4. Релизовать приоритезацию задач в 3D очереди
Это позволит снизить лаг по простым заказам. Такой подход позволяет увеличить UX и удовлетворенность клиентов

5. Реализовать отложенный расчет стоимости в MES
MES является критически важной системой и, при этом, бутылочным горлышком. Такой подход позволит разблокировать работу всей системы при проблемах на стороне MES. Также необходимо реализовать уведомления конечным пользователям, о том, что расчет стоимости будет произведен позже. Важно понимать, что это крайний случай, который, в идеале, не должен происходить никогда.

6. Очередь RabbitMQ между CRM API и хранилищем 3D моделкй
Это поддерживающая мера, призванная повысить отказоустойчивость системы

7. Кеширование в MES
Кеширование позволит ускорить ежедненвную работу, снизит нагрузку на БД и фронт

8. Реплицирование и шардирование БД
Это трудоемкая задача, которая, в конечном итоге, позволит сильно улучшить ситуацию с отказоустойчивостью и масштабированием

9. Автоматическое масштабирование приложений
Важная задача, но не самая приоритетная, так как решает довольно специфичные и редкие проблемы непридвиденных пиковых нагрузок

10. Прогноз нагрузки
Полезный функционал, но должен быть реализован после сбора всех метрик, что требует времени

11. Автотестирование и CI/CD
Важные процессы работы команды разработки, но это не поможет решить насущные проблемы системы

12. Контроль версий API и документация
Важная задача, но более административная и не требует решения здесь и сейчас. Может быть частично решена путем изменения протоколов работы команды разработки.

## Целевая архитектура через полгода

1. Реализован микросервисный ассинхронный подход
- Все ключевые сервисы взаимодействуют через RabbitMQ с retry, DLQ и приоритезацией
- MES обрабатывает расчёты асинхронно, через очередь
2. Высокая наблюдаемость системы
- Трассировка (OpenTelemetry или Jaeger)
- Метрики (Prometheus + Grafana)
- Логгирование (ELK)
- Мониторинг очередей + алерты по SLA
3. Производительность и отказоустойчивость
- Redis кеширует горячие данные MES
- БД разнесена на мастер/реплику
4. Современные dev-практики
- Автотесты + пайплайны CI/CD
- Документированные API с версионированием

## Три инициативы на ближайшие пол года
1. Асинхронный вызов MES + очередь между MES API и MES
- Решает потери заказов, снимает давление с ключевой системы
2. Мониторинг + трассировка + SLA-алерты
- Инициатива нужна для контроля, поддержки, понимания, где и почему возникают проблемы в системе
3. Очередь и приоритезация 3D-задач + кеш MES (если останется время)
- Улучшит опыт операторов, снизит жалобы, ускорит простые заказы
