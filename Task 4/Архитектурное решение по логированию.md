# Архитектурное решение по логированию

**Отображение логирования на схеме С4 можете посмотреть в папке Task 4 в файле jewerly_c4_model**

Логи:
- MES
Логируем: 
    - id заказа
    - id покупателя
    - Время начала расчета стоимости
    - Время окончания расчета стоимости 
    - trace_id
    - operation_name
    - model_id
Логи с уровнем FATAL:
    - Отказ MES API
    - Проблемы с MES DB
    - Невозможность интеграции с хранилищем 3D объектов
    - Невозможность отправки сообщений в RabbitMQ
Логи с уровнем ERROR:
    - 401/403 и 50х ошибки со стороны API
    - Заблокированный заказ или покупатель
Логи с уровнем WARN:
    - Некорректные данные со стороны MES API. Например, неправильные аутентификационные данные пользователя, невалидный токен и тд.
    - 400/404 ошибки со стороны API
Логи с уровнем INFO:
    - Статусы расчета заказа
    - Время отправки заказа в 3D хранилище 
    - Время отправки/получения сообзений из очереди
Логи с уровнем DEBUG (только для Dev окружения):
    - Запись промежуточных данных расчета
    - Отладочная информация об API (JSON запросов и ответов)
    - Детали конвертации 3D модели

2. CRM
Логируем: 
    - id заказа
    - id покупателя
    - Статусы заказа
    - Время изменения статусов
    - trace_id
    - operation_name
    - model_id
Логи с уровнем FATAL:
    - Отказ CRM API
    - Проблемы с Shop DB
    - Невозможность отправки сообщений в RabbitMQ
Логи с уровнем ERROR:
    - 401/403 и 50х ошибки со стороны API
    - Заблокированный заказ или покупатель
    - Ошибки при публикации в очередь
Логи с уровнем WARN:
    - Некорректные данные со стороны пользователей. Например, неправильные аутентификационные данные пользователя, отсутствие прав и тд.
    - 400/404 ошибки со стороны API
Логи с уровнем INFO:
    - Статусы заказа
    - Время отправки заказа в 3D хранилище 
    - Время отправки/получения сообзений из очереди
    - Успешная публикация сообщения в очередь
Логи с уровнем DEBUG (только для Dev окружения):
    - Запись промежуточных статусов заказа
    - Отладочная информация об API (JSON запросов и ответов)
    - Детали конвертации 3D модели

3. Internet Shop
Логируем: 
    - id заказа
    - id покупателя
    - Время создания заказа
    - trace_id
    - operation_name
    - model_id
Логи с уровнем FATAL:
    - Отказ Shop API
    - Проблемы с Shop DB
    - Недоступность хранилища 3D моделей
Логи с уровнем ERROR:
    - 401/403 и 50х ошибки со стороны API
    - Заблокированный заказ или покупатель
    - Ошибки при публикации в очередь (когда будет подключена очередь)
    - Ошибки загрузки 3D моделей
Логи с уровнем WARN:
    - Некорректные данные со стороны клиентов. Например, неправильные аутентификационные данные клиента
    - 400/404 ошибки со стороны API
Логи с уровнем INFO:
    - Создание заказа
    - Время отправки заказа в 3D хранилище 
Логи с уровнем DEBUG (только для Dev окружения):
    - Запись промежуточных статусов заказа
    - Отладочная информация об API (JSON запросов и ответов)
    - Детали конвертации 3D модели

4. RabbitMQ
Логируем:
    - message_id
    - trace_id
    - operation_name
    - exchange_name
    - queue_name
    - timestamp отправки/получения сообщения
    - status отправки сообщения (success, fail)
    - retry_count (если повторная отправка)
Логи с уровнем FATAL:
    - Невозможность установить соединение с брокером
    - Полная потеря очереди
    - Проблема в самом брокере (например, недоступность кластера RabbitMQ)
Логи с уровнем ERROR:
    - Ошибка публикации сообщения
    - Потеря подтверждения доставки сообщения
    - Ошибка получения сообщения из очереди
    - Ошибка десериализации/декодирования сообщения
Логи с уровнем WARN:
    - Задержка подтверждения доставки больше допустимого порога времени
    - Сообщение превышает допустимый размер, но отправлено успешно
    - Механизм ретрая запущен для сообщения
    - Некорректный формат сообщения (но сообщение не критичное и обработано с предупреждением)
Логи с уровнем INFO:
    - Успешная публикация сообщения в очередь
    - Успешное получение и обработка сообщения
    - Создание нового канала связи с брокером
Логи с уровнем DEBUG (только для Dev окружения):
    - Полные данные опубликованного/полученного сообщения
    - Информация о ретраях: сколько раз и с какими задержками было переотправлено сообщение
    - Отладка коннекторов

# Мотивация

Логирование — это один из основных инструментов для наблюдаемости работы системы. Оно позволяет:
- Быстро диагностировать технические проблемы (например, зависшие или потерянные заказы)
- Понимать, где происходят сбои на уровне бизнес-процессов
- Повышать надёжность и устойчивость работы всех приложений
- Снижать время реакции на инциденты и улучшать пользовательский опыт

Что это даст компании:
- Существенное сокращение времени поиска и устранения проблем
- Возможность обоснованно принимать решения о масштабировании или оптимизации процессов
- Уменьшение потерь клиентов и возвратов заказов из-за технических проблем
- Более высокую прозрачность процессов для партнёров, что особенно важно при работе через API
- Возможность строить отчётность и аналитику по качеству работы сервисов

Так как на данный момент ресурсов для покрытия трейсингом и логированием всей системы недостаточно выделены следующие приоритетные сервисы:
1. CRM
- CRM — это точка создания и изменения заказов
- Большинство жалоб от клиентов связано именно с потерями и некорректной обработкой заказов
- Ошибки в CRM критически влияют на весь процесс выполнения заказа (например, заказ может не попасть в производство)
- Через CRM идут входящие заказы от внешних партнёров через API, а их удовлетворенность — ключевой фактор роста бизнеса
Что даст:
- Контроль над жизеннным циклом заказа
- Быструю локализацию ошибок при движении заказа пл процессу
- Снижение количества потерянных заказов

2. RabbitMQ (передача сообщений) - на первом этапе достаточно логирования
- Очередь — это критическая связка между CRM и MES
- Потерянные или недоставленные сообщения это потерянные заказы
- При росте нагрузки вероятность проблем в очереди увеличивается
Что даст:
- Гарантированное отслеживание успешной доставки заказов между системами
- Быстрая диагностика при обрывах или потерях сообщений
- Улучшение общей надёжности системы

3. MES
- MES рассчитывает стоимость изделия, и задержки или ошибки в нём вызывают серьёзные сбои в процессе
- Проблемы в MES приводят к невыполнению заказов в срок — главной жалобе клиентов
Что даст:
- Мониторинг скорости расчётов и оперативное выявление "зависших" моделей
- Быстрая реакция на сбои в расчетах или интеграции с базой/хранилищем 3D-объектов
- Снижение рисков затяжного производства

Менее приоритетные системы для покрытия трейсингом и мониторингом:
1. Трейсинг RabbitMQ
На первом этапе достаточно логирования. Трейсинг даст дополнительную информацию о состоянии сообщений.

2. Интернет магазин
Ошибки здесь видит сразу пользователь (B2C), а влияние на производственные процессы не такое критичное.

3. Dev/Test окружения
Среды разработки и тестирования менее приоритетны для покрытия логами и трейсингом, чем продакшн. Можно отложить

# Предлагаемое решение

Логирование можно реализовать при помощи ELK стека. Это набор инструментов для извлечения, поиска, анализа и визуализации данных. Для агрегации данных можно использовать FileBeat. FileBeat это агент, которы отправляет данные в Logstash. Logstash собирает данные и отправляет их в Elasticsearch. Данные хранятся в Elasticsearch. Для визуализации используется Kibana.

* Filebeat передаёт данные в Logstach — конвейер данных.
* Logstach передаёт данные в Elasticsearch — базу данных.
* Elasticsearch обменивается данными с Kibana, инструментом для визуализации.

Доступ к логам нужно ограничить. Предлагается использовать RBAC определения уровня доступа. Доступ на чтение дается только наблюдателям и разработчикам. Полный доступ к логам дается только админам. Также доступ к логам предлагается обеспечить только из внутренней сети, попасть в которую можно только с использованием VPN. Доступ к Kibana можно организовать через SSO для админов.

Для каждой системы (CRM, MES, RabbitMQ, Shop) необходимо создать отдельный индекс в Elasticsearch

В качестве политики хранения логов предлагается использовать ILM Elasticsearch. Логи на продакшене предлагается хранить не более трех месяцев или по достижении предельного объема БД. На Dev и Test время хранения можно сократить до месяца. Размер каждого индекса предлагается ограничить 20 ГБ для избежания проблем с БД.

При необходимости, с ростом компании можно добавить шардирование индексов и разнести их на разные ноды. Это позволит улучшить отказоустойчивость Elasticsearch, но на начальном этапе можно обойтись и без этого.

Также на начальном этапе можно настроить отправку логов напрямую из Filebeat в Elasticsearch. Целевем вариантом все равно является использование Logstash, но сейчас сложное преобразование данных не требуется.

## Алертинг

Для оперативной обработки инцидентов следует настроить алертинг. Алерты можно отправлять в корпоративный мессенджер или на почту ответственных лиц. В качестве альтернативного решения можно предусмотреть систему мониторинга. Например Grafana Alertmanager

Алерты:
- Ошибки уровня FATAL и ERROR
- Падение количества логов
- Резкий рост ошибок аутентификации или авторизации
- Ошибки публикации или доставки сообщений в RabbitMQ
- Ошибки соединения с БД

В качетсве аномалий можно рассмотреть:
- Резкий рост количества записей по ключевым событиям
- Резкий рост 4хх и 5хх ошибок за короткий промежуток времени
- Нетипичная работа RabbitMQ. Напимер, слишком быстрое наполнение очереди без обработки

# Критерии выбора технологии

| Технология | Лицензия | Сообщество | Интеграция с другими системами | Развертывание | Масштабируемость |
|:-----------|:---------|:-----------|:-------------------------------|:--------------|:-----------------|
| **ELK Stack (Elasticsearch, Logstash, Kibana)** | Open Source (Elastic License для некоторых компонентов) | Очень большое и активное | Широкая поддержка через Beats, Logstash, плагины | Требует продуманной настройки (особенно для продакшена) | Отличная, при правильной настройке |
| **Grafana Loki + Promtail** | Open Source (AGPL v3) | Активное, но меньше чем у ELK | Хорошая интеграция с Grafana и Kubernetes | Легкое развертывание | Средняя — оптимально для логов с метками |
| **Splunk** | Коммерческая | Профессиональное (но меньшее по численности) | Огромное количество коннекторов | Сложное развертывание on-premise, SaaS проще | Отличная, рассчитана на enterprise |
| **Graylog** | Open Source (с коммерческими расширениями) | Небольшое, но стабильное | Базовая интеграция через плагины | Относительно простое | Средняя, требует тюнинга на больших объемах |
| **Datadog Logs** | Коммерческая (SaaS) | Активное среди пользователей Datadog | Огромная поддержка облачных сервисов и приложений | Очень простое (SaaS) | Отличная, но дорого при больших объемах |

Рекомендуется выбрать ELK Stack.

Плюсы:
- Масштабируется горизонтально (Elasticsearch умеет расти вместе с нагрузкой)
- Быстрый поиск по логам и продвинутая агрегация
- Множество интеграций (поддерживает Java, Spring Boot, C#, RabbitMQ через стандартные плагины)
- Можно построить отдельные индексы для разных систем
- Есть нативные алерты через Kibana Alerting или Watcher
- Бесплатная базовая версия (при старте очень важно для снижения затрат)

Минусы:
- Высокие требования к ресурсам
- Требуется тщательная настройка
- Сложность масштабирования
- Логистика данных

ELK - предпочтительный выбор на старте масштабируемой системы логирования, если заранее заложить время на настройку, мониторинг кластера и грамотное планирование роста логов.
